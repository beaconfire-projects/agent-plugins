# Marketing Position workflow

Use for Vendor/Client selection, finding, creating and editing Marketing positions, or extracting a supplied JD into form fields. Verify all seven tools in the tag inventory are deployed with `marketing,positions` (Vendor list: `marketing,vendors`); an old deployment with Staffing tags is not authorized by this skill.

Follow [Create orchestration](create-orchestration.md): search first; missing Vendor/Client companies can be created or receive the needed role with supported company tools, then refresh both selectors to verify eligibility/scope.

1. `marketing_list_vendors` returns only permitted vendors; `marketing_list_position_clients` returns eligible Client companies. Resolve exact returned codes; no invented identifiers or staffing default-position requirement. Admin/Manager see all vendors; AMs only their assignments. Empty scope is not an invitation to use another identity.
2. `marketing_list_positions` accepts multiple Vendor/Client codes. Use `marketing_get_position` to read the selected code, including historical TMP-POS codes, version, JD, Levels, rounds and `history`. Ask if multiple positions match. For an audit request, read the exact position first: `history` contains only that visible Marketing position's recorded time, operator, channel, action and field-level old/new values, newest first. JD history only shows `changed`; never infer previous JD from its current value. Empty history means no Marketing audit records were found, not that the position was never changed. Missing/inaccessible positions return an error before audit is read; stop rather than trying other identities, Staffing tools, REST, SQL or scripts.
3. Optional `marketing_parse_position_jd`: only supplied original JD is required (50,000 UTF-16 units). Vendor/Client context is optional and scope-checked; use `position_code` for an edit's fixed companies. Parsing never saves or audits. Treat model output as untrusted suggestions, inspect each field, do not infer missing requirements.
4. State the create plan and proceed when complete/unambiguous; updates still require before → after confirmation. Create requires title, Vendor and Client; these companies cannot change after creation. Omitted Levels default to Junior/Mid/Senior; `[]` means none. Omitted rounds default to L1/L2/C1/C2/CF; a position can also carry **special requirements** (questions candidates answer on their submission, such as OSHA Certification or Splicing Experience): `requirements` is a list of `{key, label, value_type (choice|number|text), options (choice only), is_required}`; `key` is lowercase letters, digits and underscores and must not change once answers exist; on update send the complete list (it replaces the old one); a requirement that submissions already answer cannot be removed, change type or lose an option in use; `is_required` only prompts and never blocks a submission. Adding a field such as Java years is one more requirement, not a new column; custom rounds must already exist in the unified configuration (no MCP round creation tool; use authorized web configuration rather than guessing).
5. Create with `marketing_create_position`, or update with `marketing_update_position` using the current version and only supplied changes. Empty/null optional text clears it; used Levels cannot be removed. Noop does not create an audit event. JD values are masked in audit. Persisted Position writes audit as Marketing; parsing does not.
6. Read the exact saved code again. On stale version, reload and reconfirm. On unknown write outcome, inspect current positions before retrying; no blind recreate. Missing/inaccessible is not permission to probe Staffing.

Position Detail on the web and embedded list shows Basic information, structured/original JD and Audit log; existing Position detail responses carry the same `history`. Historical Staffing audit is not included or relabeled. Only tools with a verified `marketing` tag may be used; if the deployed detail tool or its tags cannot be verified, stop and report the capability gap. Marketing creation does not insert legacy Staffing client names, so a new Client may be unavailable to old Staffing position resolution. Do not silently repair legacy data or promise Staffing workflow compatibility. Create a Submission only when part of the requested goal, using the returned Position code and the Submission duplicate-check rules; not as an unsolicited follow-on.
