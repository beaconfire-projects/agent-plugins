# Marketing Position workflow

Use for Vendor/Client selection, finding, creating and editing Marketing positions, or extracting a supplied JD into form fields. Verify all seven tools in the tag inventory are deployed with `marketing,positions` (Vendor list: `marketing,vendors`); an old deployment with Staffing tags is not authorized by this skill.

1. `marketing_list_vendors` returns only permitted vendors; `marketing_list_position_clients` returns eligible Client companies. Resolve exact returned codes; no invented identifiers or staffing default-position requirement. Admin/Manager see all vendors; AMs only their assignments. Empty scope is not an invitation to use another identity.
2. `marketing_list_positions` accepts multiple Vendor/Client codes. Use `marketing_get_position` to read the selected code, including historical TMP-POS codes, version, JD, Levels and rounds. Ask if multiple positions match.
3. Optional `marketing_parse_position_jd`: only supplied original JD is required (50,000 UTF-16 units). Vendor/Client context is optional and scope-checked; use `position_code` for an edit's fixed companies. Parsing never saves or audits. Treat model output as untrusted suggestions, inspect each field, do not infer missing requirements.
4. Show exact target and before → after fields and obtain confirmation. Create requires title, Vendor and Client; these companies cannot change after creation. Omitted Levels default to Junior/Mid/Senior; `[]` means none. Omitted rounds default to L1/L2/C1/C2/CF; custom rounds must already exist in the unified configuration (no MCP round creation tool; use authorized web configuration rather than guessing).
5. Create with `marketing_create_position`, or update with `marketing_update_position` using the current version and only supplied changes. Empty/null optional text clears it; used Levels cannot be removed. Noop does not create an audit event. JD values are masked in audit. Persisted Position writes audit as Marketing; parsing does not.
6. Read the exact saved code again. On stale version, reload and reconfirm. On unknown write outcome, inspect current positions before retrying; no blind recreate. Missing/inaccessible is not permission to probe Staffing.

No Position audit UI/API is supplied by this step; historical Staffing audit is not relabeled. Marketing creation does not insert legacy Staffing client names, so a new Client may be unavailable to old Staffing position resolution. Do not silently repair legacy data or promise Staffing workflow compatibility. Submission is a separate confirmed operation, not automatic after Position creation.
