# Create orchestration: resolve → create dependencies → reuse IDs

Applies to every create goal, especially Submission and Offer. Use only tools whose actual declared tags contain `marketing`, as individually checked in [Tool boundary](tool-boundary.md); verify the connected schema too. Missing tools, unverifiable tags or denied scope stop the affected branch. Never substitute staffing-only tools, REST, SQL or scripts.

## One goal, several calls

A clear user create request authorizes the necessary supported dependency creates, not unrelated follow-on work. Search first; reuse an unambiguous matching record. When none exists and supplied information is sufficient, briefly state the plan and create the required dependencies without a separate yes/no for each record. Ask together for missing required data, ambiguous identities/relationships or choices not determined by the request. Do not invent legal names, company types, IDs, dates or optional values. A read-only search request never authorizes creation.

This is **multiple sequential MCP calls**, not a nested-create API or atomic transaction. Each call accepts only its documented fields. Read back each success and pass its returned code to the next call. Existing records may be reused without being modified; ordinary updates, deletes and status actions still require their documented diff/confirmation. A requested Vendor/Client role addition through company create may be part of the dependency plan; flag changes on existing companies remain separately confirmed updates.

Exceptions that always retain explicit review/confirmation:
- Existing candidate-position submissions: show the pair check and ask reuse versus **separate submission**; only explicit separate-record consent permits `create_separate=true`.
- Offer: preview the exact submission's full interview set (including none) and existing offers, then obtain explicit interview-review and independent-offer confirmation. A general create goal cannot pre-confirm an unseen preview.
- HR import retains its row preview/confirmation; optional AI enrichment requires consent. Conflicts or changed versions require fresh review, not automatic overwrite.

## Actual dependencies and scope

| Goal | Resolve/create order and limits |
| --- | --- |
| Company | Search shared companies, check identity, then [company create/role attachment](company.md). Vendor/Client are roles on the same company; do not create duplicate companies for the two roles. Require `name`, `legal_name` and a supported role/flag. Vendor addition requires capabilities/unique operator identity and automatically binds the AM; never create a Person to repair that identity implicitly. |
| Person | Search email/name, then [manual Person create](create-person.md) with `first_name`, `last_name`, `email`. Admin/Manager scope required. Batch, HR recruiter and authorization use returned options; no batch/contact-role creation is available. Person is **not** candidate readiness. |
| Candidate | Search eligible candidates and, only with authorization, shared People; follow [Create candidate](create-candidate.md). Existing Person conversion sends only `person_code` and requires batch history, producing Bench. New intake sends type/legal names/email directly to candidate create—do not first create a standalone Person. Read eligibility back before Submission; AM identity/readback gaps may require authorized manual resolution. |
| Position | Search scoped positions and resolve Vendor/Client. If missing, create companies or attach the required roles, then refresh `marketing_list_vendors` / `marketing_list_position_clients`; shared-company visibility alone does not grant Vendor scope. Call `marketing_create_position(body={title,vendor,client,...})` with returned company codes. Companies are immutable on the position. Read it back and refresh the submission position selector when needed. |
| Submission | Resolve eligible candidate and scoped position; create/convert a missing candidate using the supported path above, then verify eligibility; create a missing position and its companies as above. Resolve optional employer through `marketing_search_submission_employers`; create a missing company only when its legal identity and valid role/flag are supplied, then refresh the selector. There is no `employer` company role and no need to invent Vendor/Client or PO flags. Check the pair, then create with `candidate_code`, `position_code`, optional documented details and any separately confirmed duplicate flag. `contact_name/email/phone` are text details, not Person/company-contact create requests. |
| Interview | Resolve a submission first. If absent and the create goal supplies enough data, use the Submission chain, then read `marketing_get_interview_submission` for rounds and participants. Only returned recruiters/trainers are selectable; no company-contact, trainer or round creation is provided. Follow [Interview](interview.md) for scheduling and side effects. |
| Offer | Search offers and source submissions first; reuse the intended existing offer rather than silently adding another. If a source submission is absent, run the Submission chain and retain its code. Then preview that exact submission and obtain the mandatory Offer confirmation before creating. Candidate/Position/Vendor/Client derive from the submission; none is a nested Offer create field. |

Candidate eligibility must come from `marketing_search_submission_candidates`, not a Person lookup or a supplied PER code alone. Candidate creation/conversion is available, but the selector is not a full identity directory; follow [Create candidate](create-candidate.md) for role-dependent identity lookup, unsupported conversion cases and unknown-outcome verification. If unresolved, retain IDs and stop the affected branch. C2C candidate `employer_name` has a documented internal name-based company reuse/create side effect; it is not a nested request or the Submission employer-code association.

Offer create accepts only `request_id`, `submission_code`, `interviews_confirmed`, `po_company`, optional `offer_date`, `onboarding_tentative_start_date`, `work_location`. `po_company` is the fixed Invct/BSS/BFS choice, not a company code. PO Vendor is a different, optional **update-only** association: resolve via `marketing_search_offer_po_vendors`; a missing company can be created with `is_po_vendor=true`, while an existing company's flag needs a confirmed update. Refresh the selector, then separately confirm/update the saved offer with `po_vendor_code` and current version. Rate and other update-only fields likewise require a later update, never extra create fields. Do not create interviews just to satisfy an Offer: neither Passed nor any interview is required.

## Partial failure and resumption

Keep a compact ledger of reused/created codes, current versions, pending steps and failures; keep an Offer attempt's UUID and exact payload. Successful dependencies stay saved when a later step fails or the user declines Offer confirmation. Report them and resume from the failed/pending step, reading and reusing their IDs—never replay the whole chain or automatically delete, cancel or roll back successes.

For unknown outcomes, verify state first using exact readback, identity searches, pair checks or submission previews. Absence from a scoped result is not proof of absence or rollback. If the result cannot be established, stop and report uncertainty. No blind retry; only Offer supports same-attempt UUID verification as documented in [Offer](offer.md). Sheet lag/queued follow-up does not justify recreating business records. End with saved IDs, what remains blocked and the next required input, not an all-or-nothing success claim.
