# Create a Marketing candidate

Use for a candidate goal or a missing candidate dependency of Submission/Offer. Follow [Create orchestration](create-orchestration.md): search/reuse first, ask for missing/ambiguous information together, then create without routine per-dependency confirmation. Ordinary Person creation/import does not establish candidate readiness.

## Verified contract and scope

`marketing_create_candidate(candidate={...})` declares **`tags={"marketing","candidates"}`** in `modules/marketing/mcp/candidates.py`; registered in `app/main.py`. Contract checked against Marketing `schemas/services/repos/candidates.py` in the local checkout. Verify the connected deployment's tags/schema before use; local source declarations do not establish deployed availability. Use only actually verified `marketing`-tagged tools; never staffing-only candidate detail/addable search, REST, SQL or scripts.

Creation is position-independent: admitted Admin/Manager all-vendor callers, or AM callers with an accessible Vendor. No `position` parameter. AM creator assignment is best-effort after commit; Admin/Manager are not automatically assigned. Report assignment warnings, never recreate to repair assignment. No submission, interview or offer is created by this tool.

## Search and choose a path

1. Call `marketing_search_submission_candidates(q, page, page_size)` by supplied code/email/name; paginate, compare exact identity and reuse an unambiguous eligible candidate. Its tags are `marketing,submissions`. Results contain only `code`, `name`, primary `email`, `marketing_status`; no candidate type, phone, batch or full profile. This is an eligibility-filtered selector, **not** a complete identity directory. No result does not prove the Person/candidate is absent.
2. If authorized for Person management, use `marketing_list_people(query, page, page_size)` and `marketing_get_person(code)` (`marketing,people`) for identity/contact and batch inspection. Search email/name and supplied phone; inspect returned identities, not just substring matches. People lookup includes alternate/history emails and phone records, but is still not a client-side duplicate guarantee. `current_batch` is not the full batch history. Person detail exposes `consultant_info.candidate_type`, not `is_candidate` or marketing status; `is_consultant` is not the candidate flag.
3. For AMs, these broad Person tools are unavailable: do not bypass denial. A supplied exact Person code with user-established identity can be used for conversion; the create service checks existence, candidate flag and batch. If only an ambiguous name/noncandidate identity is known, stop for authorized identity resolution rather than guessing. For a genuinely new-person request with complete identity, an empty eligibility search may proceed to create, relying on server duplicate checks—not claiming comprehensive absence. Do not use create as an identity-probing tool or retry an unknown write this way.

### Existing Person → Bench

Call **`marketing_create_candidate(candidate={person_code: "PER-…"})` only**. The only key is `person_code`; it is trimmed and uppercased. Do not send any other key, even null/default values, type or version. A Person must exist, not already have `is_candidate=true`, and have at least one batch association (not necessarily the current one). Missing batch means stop for genuine readiness correction; never manufacture HR/batch data to force conversion. Other existing-person candidate types are not supported by this create path.

The service sets the candidate flag and Bench type, preserves personal data and existing marketing status; a missing consultant row starts `In Preparation`. The current repository also resets `supplier_company_id` to null on conversion; disclose this effect if relevant, do not promise every consultant field is preserved. No personal-data patch is included. If an existing preserved status prevents submission eligibility, creation is not permission to reset it: standalone candidate status/update tools remain outside this inventory.

### New Person + candidate, one call

Do **not** create a standalone Person first: the existing-person route requires batch information and always converts to Bench. Send required `candidate_type`, `first_name`, `last_name`, `email`. Types: `Skip Training`, `Staffing - W-2`, `Staffing - C2C`, `Staffing - 1099`; these are values in the Marketing schema, not permission to use Staffing tools. Ask for type/legal names when missing; `Bench` is not a new-person type. The new candidate starts `In Preparation`.

Optional fields, only when supplied:
- `middle_name`, `preferred_name`, `phone` (at least 10 digits), `yoe` (integer 0–40), `gender`, `linkedin_url`, `facebook_url` (each at most 300 characters), `phone_preference` (iOS/Android), `laptop_preference` (Windows/Mac).
- `work_authorization`: USC, GC, GC-EAD, H1B, H4-EAD, OPT, STEM OPT, CPT, C08 EAD, Asylum EAD, Other EAD; `work_authorization_start_date`, `work_authorization_expires` are ISO dates, expiry not before start. Dates without a type are stored with type `Unknown`; explain that rather than inventing a visa type.
- `address_street`, `address_city`, `address_state`, `address_postal_code`: all four together or all empty; two-letter US state (this candidate service includes DC), ZIP `12345` or `12345-6789`. `date_of_birth` must be a real date in exact `mm-dd-yyyy` format, year 1900–2100, unlike ISO authorization dates. Minimize sensitive data in replies; no SSN field.
- `work_arrangement_preference` (Remote/On-site/Hybrid/Open), `relocation_willingness` (Open/Conditional/Not open), `preferred_time_zones` (Eastern/Central/Mountain/Pacific), `location_note`. Conditional relocation requires a nonblank location note (at most 2000 characters); time zones are deduplicated in Eastern/Central/Mountain/Pacific order. Do not infer restrictions from time-zone preferences.
- `employer_name`, only for Staffing - C2C, optional; see below.

Unknown fields are rejected. In particular, no `position`, `level`, `batch_id`, candidate status, responsible-AM list, employer code or nested company/person request is accepted.

## C2C employer is a name-based special case

Before supplying `employer_name`, search `marketing_list_companies(q)` and inspect exact names/identity with `marketing_get_company`; both have `marketing,companies` tags. Resolve ambiguous names with the user. Candidate create itself matches company display name case-insensitively after trimming, reuses the first exact match, or creates a `TMP-C2C-…` company flagged as C2C. It does not accept `employer_code`, company roles, flags or legal-name objects, and does not return the employer company code. If duplicate exact display names cannot be safely distinguished through this name-only contract, stop that association rather than let it pick an unintended company.

This documented internal side effect is not a nested-create request and does not require a preceding company create solely to satisfy C2C intake. Do not invent Vendor/Client roles for it. Afterwards search/read the company when relevant; this verifies the company, not the supplier link (no allowed full candidate detail exposes that link). Submission `employer_code` is a separate optional association: resolve it through the submission employer selector; do not assume it is copied from the candidate or that the candidate's employer is a position Vendor/Client.

## Readback, errors and unknown outcomes

- Success returns only `code`, `name`, `candidate_type`, `warnings`, not version/full profile/status. Record that success immediately. Re-query `marketing_search_submission_candidates(q=returned_code)` and compare the exact code to verify eligibility before Submission; then continue position/pair-check/Submission/Offer orchestration. A missing selector result does not undo a successful create/conversion. Report saved ID and blocked eligibility; do not recreate or automatically change status.
- Authorized Admin/Manager may additionally call `marketing_get_person` (`marketing,people`) for supported current fields. Do not claim full address, supplier, candidate-flag or assignment readback: those are not Person detail fields. No allowed general candidate-detail tool is provided. Candidate create/conversion and creator-assignment audits use `module=marketing`; `marketing_get_person_history` currently reads only `module=staffing`, so it cannot verify these new audits. Empty or older Person history proves neither failure nor success of this attempt; no verified Marketing candidate-audit reader is available.
- `duplicate_identity` checks primary and all alternate/history emails, plus primary/current phone identities by last 10 digits; it returns the owner code. Inspect/reuse the correct identity or clarify, never change contact data to evade duplication. A same-name/different-email warning is nonblocking, not proof that identities are distinct or authorization to merge them.
- `duplicate_candidate`: do not convert again; verify identity/eligibility and reuse if appropriate. `invalid_candidate`: correct the actual missing/type/batch/field issue, not fabricated defaults. `forbidden`/`not_found`: stop within authorized scope.
- Unknown `candidate_operation_failed` or transport outcome: first search by known code, otherwise supplied email/name; authorized Person lookup can help locate the identity and inspect supported current fields, but Person history cannot verify this Marketing audit. Selector presence proves current eligibility, not every requested field or attribution to this attempt. No candidate request UUID/idempotency key exists. If identity, candidacy or outcome remains uncertain, **stop and report a verification gap**, retain payload/known IDs and request authorized manual verification outside this automated workflow; never resend create/conversion to test whether it committed.

In particular, AMs cannot safely enumerate noneligible/noncandidate identities, and an existing-Person conversion preserving an ineligible status may be invisible to the candidate selector even after success. Person lookup alone cannot settle its candidate flag. Preserve all successful dependencies and resume only from verified state; do not automatically delete, reimport or recreate any Person/candidate/company.
