# Staffing lookups and changes

Use only the `marketing_*` and `insights_*` tools of the connected `marketing-system` MCP server. Do not call the REST API, SQL, scripts or another plugin, and never invent IDs, versions or option values. If the tools are not visible, report a connection problem instead of guessing.

## Pick the workflow

| The user wants | Read this reference |
| --- | --- |
| Look up interviews: one candidate's interviews and results, one interview by ID, or a schedule by round and date (read only) | `references/interview.md` (Looking up interviews) |
| Change an interview's date, time, time zone, result, score, link, recruiter, interviewer or notes | `references/interview.md` |
| Record that a candidate got an offer, or find candidates who passed L2 and have no onboarding record yet | `references/onboarding-create.md` |
| Set, change or clear the start date | `references/onboarding-start-date.md` |
| Confirm that the person actually started, create / update / cancel an offboarding, or confirm that the person left (Remap / Quit / Fired) | `references/onboarding-start-end.md` |
| An offer was canceled (the candidate declined or the company rescinded it), or a cancellation is undone | `references/onboarding-cancel.md` |
| Add a candidate (an existing person or a new one), or change candidate information (name, contact, visa, address, date of birth, LinkedIn, Facebook, devices, type, level, rate, status) | `references/candidate.md` |
| Submit a candidate to a position, read a submission, or change its pay rate, availability, same client history or C2C employer | `references/submission.md` |
| Create interview slots, put one or several candidates on slots, release or cancel slots, or reschedule after Need to Reschedule | `references/slots.md` |
| Delete an interview or an onboarding record created from wrong data (candidates are deleted by an Admin in the web back office) | `references/delete.md` |
| Process the mailbox or read the client chat group now | `references/ingest.md` |
| A statistics question: how many, what share, by level / visa / status / round, per week or month, how a number changed (counts only, read only) | `references/insights.md` |

One message may contain several requests; handle them one at a time, each with its own confirmation. **The exception is a batch of the same slot action** (creating slots for several recruiters, or putting several candidates on slots): that gets one confirmation table for the whole batch, as described in `references/slots.md`.

## Rules for every workflow

1. **Resolve to exactly one record first** (not for statistics questions: those go to `references/insights.md` and need no record).
   - A Candidate ID (`PER-…`) goes straight to `marketing_get_candidate_detail` (by person, no position needed; it also lists the candidate's submissions).
   - A Submission ID (`SUB-…`) goes to `marketing_get_submission`.
   - A name goes to `marketing_search_candidates` with `query` alone, no other filter (words in any order, case and single letters ignored; the ID and the email work too). If more than one candidate matches, or the match is not clearly the person, list the candidates (ID, name, email, current status) and ask which one. Never pick for the user.
   - An Interview ID (`INT-…`) goes to `marketing_get_interview`. If it is not found, ask for the candidate's name or ID. If the server does not offer `marketing_get_interview` yet, find the code with `marketing_list_interviews` (`limit=500`).
   - An Onboarding ID (`ONB-…`) goes to `marketing_get_onboarding`.
2. **Read before writing.** Every update needs the current `version` from the record you just read. If a write is rejected as stale, read again, tell the user what changed, and ask again before retrying.
3. **Validate choices.** Call `marketing_list_options` once and only use its values for results, rounds, interview times, time zones, recruiters, states, work authorizations and levels. Interview times are fixed dropdown values (for example `5:15 PM`); if the user gives a time that is not in the list, show the nearest allowed values and ask.
4. **Confirm before every write.** When a tool has a `dry_run` (creating slots, holding slots), use it to build the confirmation table from what the server says it will do, then send the same request without `dry_run` after the yes. Show a short table of `field: old → new` for the one record (a batch of slot actions: one table with a row per item), say which tool will run, and wait for a clear yes. A question, a correction or silence is not a yes. Only send the fields being changed.
5. **Report the result honestly.** After the write, restate what was saved from the tool's response (IDs, new values, resulting status). If the tool returns an error, show the message and do not claim success or retry silently.
6. **Time and dates.** Interview times are business time (US Eastern, labelled `EST`) unless the user names another zone. Dates are `YYYY-MM-DD`; resolve relative dates ("next Monday") against today and show the exact date for confirmation.
7. **Candidate profile.** The name as on the ID is the candidate's own First / Middle / Last name, and Preferred is the name the candidate goes by. Years of experience, visa type and dates, address, phone, date of birth, gender, LinkedIn, Facebook and the phone / laptop preference are the **person's** fields: read them with `marketing_get_candidate_detail` and change them with `marketing_update_candidate` (see `references/candidate.md`), showing `old → new` in the confirmation. Pay rate, availability, same client history and the C2C employer of one position are the **submission's** fields (`marketing_update_submission`, see `references/submission.md`). Only the last 4 digits of the SSN are stored (`marketing_get_candidate` with `include_profile=true`, changed with `marketing_update_candidate_submission`): if the user gives a full SSN, say that only the last 4 will be saved. The change history shows address, date of birth and SSN as `changed`, without values.
8. **Derived fields.** Offer Status, Start Date and Current Status are computed from the onboarding record, the interviews and held slots (a canceled offer clears Offer Status and Start Date and makes the candidate Candidate Withdrew or Company Dropped, see `references/onboarding-cancel.md`; a confirmed start makes the candidate Active, and a confirmed end makes the candidate Remap, Quit or Fired, see `references/onboarding-start-end.md`) (`L1 Slot Held` / `L2 Slot Held` while a candidate holds a slot with no interview yet). Never try to set them on the candidate or an interview; use the onboarding workflows.
9. **History.** Every write is recorded with who, when and what changed. When the user asks "who changed this" or "what changed", use `marketing_get_history`.
10. **L2 Passed means an offer is next.** Whenever an interview write (`marketing_update_interview` or `marketing_create_interview`) returns `onboarding_suggestion`, do not end with the interview and do not ask the user: right after the interview save succeeds, call `marketing_create_onboarding` with the suggested offer date (see `references/onboarding-create.md`) and report both results in the same reply. The user's confirmation of the interview change already covers it. In a batch, create one record per suggestion and report one row per candidate. If the interview save failed, create nothing. Candidates who passed L2 earlier and still have no onboarding record are found with `marketing_search_candidates` and `current_status` `L2 Passed`.
11. **Vendor scope.** Every tool only works on the vendors the user can see (an AM: the vendors they are responsible for; a manager or admin: all of them). A candidate, interview or onboarding outside that scope is answered with `Not found`, exactly like a record that does not exist: say that it was not found or is not available to the user, never guess an ID, and do not try another tool to reach it. Candidates in the marketing pool (`marketing_status` In Preparation or In Marketing) are meant to be shared by every AM, but showing a pool candidate of another vendor is not available yet: for now an AM without access to the candidate's vendor still gets `Not found`. See `references/candidate.md` for the marketing status.
